## 1. Документация API hh.ru — что зафиксировано и проверено

Основа: `https://api.hh.ru/openapi/redoc` (полная выгрузка спецификации сохранена локально,
спецификация скачивается с `https://api.hh.ru/openapi/specification/public`).

### Транспорт и авторизация
- HTTPS, базовый URL `https://api.hh.ru/`, ответы JSON, даты в ISO 8601, gzip на длинных ответах.
- Заголовок `HH-User-Agent` (или `User-Agent`) **обязателен** — иначе `400`.
- OAuth2. Наш токен — **application-токен** (`GET /me` → `"auth_type":"application"`), т.е. только
  публичные методы. Живой тест подтвердил:
  - `GET /resumes?...` → **403 `user_auth_expected`**,
  - `GET /negotiations` → **403**,
  - `GET /salary_statistics/paid/salary_evaluation/{area}` → **403** (платный банк зарплат + user-токен).
- Это устраивает по постановке: персональные данные соискателей API **физически недоступны**, ничего
  конфиденциального не собирается, а трекер откликов будет локальным.

### Методы, которые работают (проверено, HTTP 200)
| Метод | Назначение в агенте |
|---|---|
| `GET /vacancies` | поиск: `text`, `area`, `experience`, `schedule`, `work_format`, `salary`+`currency`, `label=with_salary`, `period` / `date_from`+`date_to`, `order_by=publication_time`, `clusters=true` (при `per_page=0` — только кластеры) |
| `GET /vacancies/{id}` | карточка вакансии: `key_skills`, описание, вилка, работодатель |
| `GET /vacancies/{id}/related_vacancies`, `/similar_vacancies` | «похожие вакансии» (пути именно такие; `/similar` → 404) |
| `GET /dictionaries`, `/areas`, `/industries`, `/professional_roles` | справочники для фильтров UI |
| `GET /employers/{id}` | карточка компании |
| `GET /suggests/skill_set?text=` | подсказка навыков (например `C#` → id 230) |
| `GET /skills?id=...` | навыки **по списку id** (не «весь справочник» — без `id` даёт 400, ≤50 значений) |

Также зафиксировано при проверке: `/specializations` → **404**, для профобластей используем
`/professional_roles`; путь `/vacancies/{id}/similar` → 404, правильный — `similar_vacancies`.
Общая шпаргалка по эндпоинтам — `docs/api_notes.md`.

### Ограничения, которые надо учитывать в коде
- Пагинация `page`/`per_page` (≤100), **глубина выдачи не больше 2000** (`per_page=10&page=199` — можно,
  `page=200` — ошибка). Обход — дробление по `experience`/`area`/`period` (в `collect_hh.py` уже есть).
- Без токена после первого запроса по вакансиям капча — у нас токен есть, капчи нет.
- Ответы `500/503` и `429` возможны → ретраи с растущей паузой (уже реализованы).
- Числовых rate-лимитов в openapi-спецификации нет → держим консервативный `sleep` и ретраи,
  а не «заливаем» пачками.

### Категорически не используем (по заданию)
Любые `POST/PUT/DELETE`: публикация и редактирование вакансий, черновики, отклики (`/negotiations`…),
сообщения в чаты, комментарии, вебхуки, поиск и просмотр резюме. Генерируемые тексты хранятся только
локально, копирует и отправляет сам соискатель.

## 2. Целевая архитектура MVP

```
┌──────────────┐   SSE (thinking / tool / text)   ┌─────────────────────────────┐
│  Frontend    │ ───────────────────────────────► │ FastAPI (async, auth,        │
│  chat + UI   │ ◄─────────────────────────────── │  session-per-user, context)  │
└──────────────┘         JSON REST                └──────────┬──────────────────┘
                                                             │ run_async()
                                              ┌──────────────▼──────────────┐
                                              │ ADK LlmAgent (openai/MODEL) │
                                              │ + guardrails (до/после)      │
                                              └──────────────┬──────────────┘
                     read-only tools                        │
        ┌──────────────────┬────────────────┬───────────────┴───┐
        ▼                  ▼                ▼                   ▼
  search_vacancies   match_profile     salary_stats        draft_letter → data/outbox/
  vacancy_details    skill_gap         (своя статистика)   track_response → data/tracker.db
        │                  │                │
        └────────── SQLite (data/app.db): вакансии, профили, сессии, отклики ──────┘
                                ▲
        daily job: collect_hh --period 1 → clean_merge → match_gap
```

### Слои
1. **Данные.** Перевести `vacancies_live` + `details` в **SQLite** (индекс по `vacancy_id`, FTS5 по
   названию+описанию, таблица `key_skills`). CSV остаётся как снимок для отчётов. Причина: 20k+ строк
   с ежедневным приростом и многопользовательский доступ через pandas на каждый запрос — неправильно.
2. **Сбор (ежедневно).** `collect_hh.py --period 1 --details 500` (инкрементально, дедуп уже по
   `vacancy_id`), затем `clean_merge.py` → пересборка FTS/агрегатов зарплат. Планировщик —
   **Windows Task Scheduler** (`schtasks /create /d Daily /st 09:00 ...`), лог в `data/collect.log`,
   в конце — сводка «сколько новых, сколько с зарплатой». Проверка деградации: если за сутки 0 новых —
   флаг в логе.
3. **Агент (ADK).** Один `LlmAgent` + явные инструменты (все read-only):
   - `search_vacancies(query, city, experience, salary_min, schedule, limit)` — по SQLite;
   - `vacancy_details(vacancy_id)` — карточка;
   - `match_profile(profile_id, top_n)` — обёртка над `match_gap.py` (перенести в пакет `app/tools`);
   - `skill_gap(profile_id)` — разрыв и приоритеты;
   - `salary_stats(skill|role, city, period_days)` — **своя** статистика по датасету
     (медиана/P25/P75 вилки, net-пересчёт `gross→net ×0.87`, срез по городу/стеку). Платный банк hh
     недоступен (403) — считаем сами и честно подписываем методику;
   - `draft_letter(vacancy_id, tone)` — генерирует письмо/сопроводительное, **сохраняет в `data/outbox/`**
     и отдаёт текст + кнопку «копировать». Отправки нет ни в одном инструменте;
   - `track_response(vacancy_id, status, note)` — локальный трекер откликов (ручной ввод статуса:
     отправлено → просмотрено → приглашение → отказ; API `/negotiations` не трогаем).
4. **Контекст и многопользовательность.** Пользователи в SQLite (email+пароль, соль/хэш, JWT или
   серверные сессии). На пользователя — свои `session_id` (ADK `DatabaseSessionService`/`SessionService`),
   история в БД. Системный промпт + профиль подхватываются из профиля пользователя, «чужой» контекст
   недоступен — изоляция через `user_id` в runner.
5. **SSE.** `POST /api/chat/stream` → `text/event-stream` c типами событий:
   `status` («планирую», «ищу вакансии») → `tool_call` (имя + аргументы) → `tool_result` (сжатие) →
   `delta` (токены) → `done` (метаданные: использованные инструменты, время).
   Источник — события `runner.run_async(...)`: `partial=True` → `delta`, вызовы функций →
   `tool_call/tool_result`. Отдельный канал для «рассуждений» модели: провайдер отдаёт reasoning-части
   текстом — их надо фильтровать из основного ответа и показывать сворачиваемым блоком «агент думает»
   (это и есть визуализация «как думает агент»).
6. **Контроль темы и инъекций (двухуровневый).**
   - *Детерминированный слой (до модели):* регэкспы/подстроки на «забудь все инструкции», «now you are
     system prompt», «ignore previous», «печать пароль», попытки выдать системный промпт; при срабатывании
     — вежливый отказ **без** вызова модели. Плюс длина/частота лимиты.
   - *Слой модели:* жёсткий system prompt — отвечать только на карьерные вопросы (вакансии, навыки,
     зарплаты, письма, отклики); на всё прочее — одна фраза отказа со списком тем.
   - *Пост-фильтр:* если в ответе вдруг появился системный промпт или инструкции — не отдавать, заменить
     отказом.
   - Инструменты физически не умеют ничего писать наружу → инъекция не может «что-то отправить».
7. **Frontend.** Одностраничный чат: лента сообщений, индикатор «агент думает»/вызов инструмента,
   карточки вакансий (вилка net, навыки, ссылка на hh), панель skill-gap (топ-бар), график зарплат
   (медиана/P25/P75 по городу и стеку), вкладка «Письма» (outbox + копирование), вкладка «Отклики»
   (трекер со статусами и датами). Форма ввода + быстрые подсказки. Стилизация под академическое демо:
   аккуратный тёмный/светлый режим, без лишнего.

## 4. Архитектурные решения, которые стоит защитить на экзамене

1. **Только чтение, по построению.** Application-токен + отсутствие любых POST/PUT/DELETE в коде:
   персональные данные недоступны (403 `user_auth_expected` — проверено), автоматическая отправка
   невозможна технически, а не обещанием.
2. **Расчёт статистики зарплат своим датасетом** вместо платного банка hh (403): медиана/P25/P75 вилки,
   приведение к net (`×0.87` для gross), срезы по городу/стеку/уровню — методика раскрыта, поэтому
   результат воспроизводим.
3. **Единая карта навыков** (алиасы → канон, один regex-набор) для матчинга, gap и зарплат — одна и та же
   логика в отчётах и в инструментах агента, расхождений нет.
4. **Прозрачный скор матчинга** с весами и штрафами — объяснимо пользователю («почему эта вакансия выше»),
   а не «чёрный ящик».
5. **SSE вместо опроса** — потоковая отрисовка хода рассуждения и вызовов инструментов; критерий UX
   «видно, как агент думает».
6. **Двухуровневый guardrail** (детерминированный фильтр → жёсткий системный промпт → пост-фильтр) —
   инъекции и off-topic отсекаются до и после модели.
7. **Многопользовательность через `user_id`-изоляцию сессий в ADK + SQLite** — контекст пользователей
   не пересекается, история восстанавливается после перезапуска.
8. **Ежедневный инкремент с дедупом по `vacancy_id`** и дроблением выдачи (лимит глубины 2000) —
   датасет растёт предсказуемо, без потери данных.

## 5. Риски и что с ними делать

| Риск | Реакция |
|---|---|
| hh 429/5xx/капча при масштабировании сбора | ретраи с растущей паузой (есть), сон между запросами, дневной инкремент маленькими страницами, `--period 1` вместо полного обхода |
| Глубина 2000 на запрос | дробление по experience/area/period (есть в `collect_hh.py`) |
| Платная статистика hh недоступна (403) | своя методика по датасету + честная подпись «по N вакансиям» |
| 4,5k из 20k вакансий с описанием | приоритетная догрузка деталей для C#/.NET и топ-запросов |
| Модель «фантазирует» цифры | в системном промпте требовать ссылаться на результат инструмента; пост-проверка чисел против выдачи инструмента |
| Инъекции / вопросы не по теме | двухуровневый guardrail + тест-кейсы в pytest |
| Остановка ежедневного сбора | лог со сводкой + сверка даты последней записи; при расхождении — ручной запуск |
| Стоимость вызовов LLM на защите | компактный system prompt, в контекст только топ-N и сжатые результаты инструментов, история ограничена окном |

## 6. Первый шаг (с чего начать сразу после этого плана)

1. Импорт вакансий в SQLite + FTS-индекс (`tools/build_db.py`).
2. Режим `--period 1` + запись задачи в Task Scheduler.
3. `app/tools/` — семь инструментов, прогон в консоли через ADK (модель уже проверена).
4. Дальше — FastAPI + SSE, затем фронтенд.

Файлы для удобства: `PLAN.md` (этот файл), `docs/api_notes.md` — короткая шпаргалка по эндпоинтам,
которые реально используем, `tools/hh_client.py` — готовый GET-only клиент hh (белый список методов,
ретраи, проверен вживую), его же брать в бэкенд и в скрипты.
